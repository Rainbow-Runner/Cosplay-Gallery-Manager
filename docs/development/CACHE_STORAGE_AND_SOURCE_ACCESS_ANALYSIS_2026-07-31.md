# CGM缓存占用与来源访问分析

> 日期：2026-07-31
> 范围：本机1.5业务测试部署、当前CGM实现、仓库保留的原Stash实现
> 初始审计决策：先增加缓存位置与占用的只读显示
> 2026-07-31后续确认：`CARD_480`保留为BASE，`LIGHTBOX_4096`改为按需生成的ENHANCED可回收缓存，并开放可回收容量上限设置

## 1. 本机缓存占用实测

本机媒体库`/home/rainbowrunner/cos/Collection`包含108个受支持媒体文件，逻辑大小
354,160,840 bytes（337.75 MiB），目录磁盘占用约338 MiB。CGM缓存目录
`/home/rainbowrunner/.cache/cosplay-gallery-manager`包含216个普通文件，逻辑大小
156,263,337 bytes（149.02 MiB），文件系统分配占用约152 MiB。

| Variant | 文件数 | 逻辑大小 | 缓存占比 | 单Item平均 |
| --- | ---: | ---: | ---: | ---: |
| `CARD_480` | 108 | 3,733,456 bytes（3.56 MiB） | 2.39% | 33.76 KiB |
| `LIGHTBOX_4096` | 108 | 152,529,881 bytes（145.46 MiB） | 97.61% | 1.35 MiB |
| 合计 | 216 | 156,263,337 bytes（149.02 MiB） | 100% | 1.38 MiB |

因此：

- 缓存逻辑大小约为来源媒体的44.1%；
- 真正的480卡片缩略图只占来源媒体的约1.05%；
- 4096 Lightbox派生图占来源媒体的约43.1%，是当前比例异常的决定性来源；
- 按当前样本线性估算，10,000张同分布静态图约产生0.32 GiB卡片图和13.15 GiB
  Lightbox图，合计约13.48 GiB，不含未来动画、视频或增强派生资源。

以上是调整前的实测：扫描会同时排队`CARD_480`和`LIGHTBOX_4096`，且两者原本都属于BASE。
现已改为扫描只生成`CARD_480`；`LIGHTBOX_4096`在首次打开对应静态图时排队生成并归入
ENHANCED，因此管理页的可回收上限会约束其长期占用。已有Lightbox文件在启动时只迁移数据库
层级、不立即删除，之后按实际访问时间参与LRU。

## 2. 原Stash的空间处理方式

仓库保留的原Stash实现采用了不同取舍：

1. 图片缩略图最长边固定为640，输出JPEG；
2. 原图两边都不超过640时不生成缩略图；
3. 缩略图可以扫描时生成，也可以首次请求时即时生成；
4. `write_image_thumbnails`可关闭落盘；关闭后即时结果直接返回而不长期保存；
5. 路径以源内容Checksum命名，相同内容可以命中同一缩略图；
6. Lightbox的完整图片请求直接读取来源媒体，不为每张静态图片常驻一份4096派生图；
7. Generated Content提供单独的清理任务，动画预览、视频预览、Sprite和Transcode按实际功能
   选择生成，其中Transcode被文档明确提示会显著占用空间。

原Stash因此以较少的派生存储换取Lightbox浏览时直接读取原图。CGM当前相反：普通浏览完全
使用受控缓存，不暴露或直接提供来源文件，但代价是扫描后常驻4096派生图。两者的安全边界和
I/O目标不同，不能只比较“缩略图目录”总量而忽略Lightbox策略。

本轮已落实前两项方向，后续仍可继续评估其余方向：

- `LIGHTBOX_4096`由扫描时全量生成改为首次需要时生成；
- 将Lightbox调整为有上限、可重建的缓存层，并补齐缺失资源重排队；
- 评估2048/2560等显示尺寸和编码质量是否满足实际屏幕；
- 对同内容媒体评估派生资源去重；
- 已有文件通过幂等迁移纳入ENHANCED，默认50 GiB上限下不会因本次部署直接删除。

## 3. 原始媒体访问边界

### 会访问来源媒体内容

| 操作 | 来源访问行为 |
| --- | --- |
| 显式`Scan gallery source`/重扫 | DIRECTORY逐个打开受支持媒体并完整读取，以计算完整BLAKE3；ZIP/CBZ会完整解压读取每个媒体Entry |
| 扫描后的BASE派生任务 | 每个Variant任务单独打开一次来源；普通静态图只预生成480，因此扫描后通常再读取来源一次 |
| 首次打开静态图Lightbox或媒体详情 | 显式排队4096代理任务，后台读取一次来源；已经命中CGM或浏览器缓存时不再读取来源 |
| RAW、动画、视频派生 | 工作者把来源路径交给dcraw/FFmpeg；归档Entry会先解压到缓存`tmp`，任务完成后删除临时文件 |
| 来源内容变更后的显式重扫和重处理 | 重复执行上述读取，用于建立新`content_revision`及其派生资源 |

扫描本身完整读取一次，普通静态图片随后由BASE任务再读取一次。因此首次导入通常发生两轮
来源内容读取；用户第一次打开某张静态图的大图时，按需后台任务才为该Item增加一轮读取。

### 只访问目录结构、Sidecar或文件元数据

| 操作 | 行为 |
| --- | --- |
| `Scan selected library`发现Candidate | 遍历目录、识别扩展名、`.cosplay-root`和`.cosplay.json`；归档读取Central Directory，不读取每张媒体的完整内容 |
| 导入Candidate为DRAFT | 只写产品数据库，不扫描媒体内容 |
| Manifest Push/Pull/冲突检查 | 只访问`.cosplay.json`或Coser Manifest，不读取图片/视频内容 |
| 管理页缓存状态 | 只遍历缓存目录并读取普通文件的大小元数据，不读取缓存文件内容，也不访问来源媒体 |

### 日常浏览只访问缓存

- 首页、Gallery列表、Coser作品分页和Related卡片请求`CARD_480`或视频静态Poster；
- Gallery详情媒体网格请求`CARD_480`；
- 打开静态图Lightbox或媒体详情时，若`LIGHTBOX_4096`已存在则只请求缓存；否则先显示
  `CARD_480`，通过幂等接口排队后台生成并轮询该Item状态；
- 视频/动画详情只会请求数据库已授权的Poster、Preview或Playback派生资源；
- GraphQL详情、搜索、时间线、关系、Favorite、Rating和历史只访问产品数据库；
- 浏览器收到派生资源的`private, max-age=31536000, immutable`，已命中的浏览器缓存甚至不会再次
  请求本机CGM；未命中时本机HTTP处理器只打开CGM缓存文件；
- 缓存文件缺失时当前处理器返回404，不会在浏览请求中回退读取来源媒体，也不会即时生成。

因此列表、卡片和网格浏览不会唤醒、读取或向浏览器暴露来源媒体盘；首次查看尚无大图缓存的
静态Item会显式触发后台媒体处理读取来源，但HTTP响应仍只服务生成后的CGM缓存，不直接服务
原图。这与原Stash Lightbox直接读取原图的策略仍存在明确差异。

激活Gallery、编辑元数据/Cast、搜索、分页、收藏、评分、数据库备份和普通完整备份不会读取
来源媒体内容；完整备份也明确排除来源媒体和派生缓存。

## 4. 本轮管理页改动

Manage → Settings的`Generated cache`区域显示：

- 启动配置实际解析后的绝对缓存路径；
- 当前普通缓存文件逻辑大小；
- 当前普通缓存文件数量。
- 数据库引用的永久BASE字节数与可回收ENHANCED字节数。
- 以GiB编辑的可回收缓存容量上限；位置仍不可在页面修改。

后端通过Server运维服务读取启动级`cache_path`，GraphQL Resolver不直接取得来源路径能力；
遍历不跟随符号链接，按请求Context支持取消。页面没有位置输入、迁移、手工清理或重建按钮，也
不会修改`cgm.json`。容量上限写入既有带revision运行时设置；后台每分钟执行ENHANCED LRU，
永不删除BASE或来源媒体。该统计只在打开Settings并发出查询时执行，不轮询缓存目录。

## 5. 2026-08-16 混合原图与动画预览策略更新

- 上文“日常浏览只访问缓存”仍适用于首页、Gallery卡片、Coser作品、Related、Scrubber和静态Gallery网格；这些入口继续只使用BASE Poster/Card。
- 用户显式打开Lightbox或单媒体详情时，前端先向认证不透明原图端点发出HEAD。JPEG、PNG、静态WebP同时满足不超过20MiB且宽高不超过4096时直接读取来源原图；不满足时继续使用`LIGHTBOX_4096` ENHANCED代理。RAW始终使用代理。
- GIF/动态WebP的Lightbox和单媒体详情读取未经重编码的完整原动画。DIRECTORY使用已打开且复核身份的文件描述符；ZIP/CBZ Entry经受限临时物化后服务精确字节，请求结束即删除临时文件。
- Gallery详情网格只有进入视口且处于前4项播放槽的动画才请求`ANIMATED_PREVIEW`。该ENHANCED WebP最长边480、最高15FPS、循环但保持完整原始时长；离开视口切回BASE Poster，`prefers-reduced-motion`下完全不请求动画预览。
- 因此显式查看合格原图或原动画会访问来源媒体；普通列表/网格浏览仍不会。已有`LIGHTBOX_4096`不会主动删除，后续由既有ENHANCED LRU自然回收。
